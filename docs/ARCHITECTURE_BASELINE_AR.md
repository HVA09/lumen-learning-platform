## 3. Backend — الوضع الفعلي

### ما هو موجود

البنية الحالية تستخدم مجلدات منفصلة:
- `app/auth/`: المصادقة والتحقق الثنائي.
- `app/routers/`: مسارات API حسب مجموعات وظيفية مثل الاختبارات والواجبات والملفات والفوترة والفصول.
- `app/models/`: نماذج SQLAlchemy، وعددها 21 ملفاً تقريباً ضمن المجلد.
- `app/schemas/`: مخططات التحقق وواجهات الطلب/الاستجابة، وعددها 16 ملفاً.
- `app/services/`: خدمات ومنطق أعمال، وعددها 17 ملفاً، مع حزمة فرعية لمزودي الدفع.
- `app/content/`: بيانات المحتوى وإدارته.
- ملفات أساسية مثل `config.py`, `database.py`, `dependencies.py`, `logging_config.py`, و`main.py`.

يقوم `main.py` بإنشاء تطبيق FastAPI وتسجيل مسارات المجالات مباشرة. كما يستورد `app.models` لضمان تسجيل النماذج في `Base.metadata` قبل استخدام Alembic.

### نقاط قوة موجودة

1. توجد حدود أولية واضحة بين المسارات والنماذج والمخططات والخدمات.
2. منطق تصحيح الاختبارات موجود في `services/quiz_logic.py` كدوال مستقلة عن FastAPI وقاعدة البيانات، وهذا مثال جيد على منطق يمكن اختباره منفرداً.
3. توجد اختبارات منفصلة لمجالات مثل المصادقة والاختبارات والواجبات والملفات والفوترة وLTI والتكرار المتباعد.
4. ترحيلات قاعدة البيانات تُدار بواسطة Alembic، واختبار CI يشغّل الترحيلات على قاعدة PostgreSQL نظيفة.

### نقاط تحتاج إلى تنظيم

1. **الوحدات ليست مجمعة حسب المجال بالكامل:** النماذج والمخططات والمسارات والخدمات موزعة في مجلدات عامة منفصلة. هذا الفصل مفيد، لكنه يجعل فهم ميزة معينة يتطلب التنقل بين مجلدات كثيرة.
2. **بعض منطق الأعمال موجود داخل ملفات المسارات:** على سبيل المثال، `routers/quiz.py` يحتوي على سير عمل بدء المحاولة والتحقق من فتح الموضوع وتسجيل النتائج وتحديث الإتقان، بينما يستدعي أجزاء من المنطق من `services/quiz_logic.py`. و`routers/assignments.py` يحتوي على قواعد رؤية الواجبات والتحقق من صلاحيات إدارتها واستعلامات التسليم.
3. **بعض ملفات البنية مشتركة على مستوى التطبيق:** مثل `notifications.py` و`audit.py` و`tasks.py`. يجب تحديد ما إذا كانت خدمات مشتركة أم جزءاً من مجال معين قبل نقلها.
4. **لا توجد طبقة API ذات إصدار واضح في المسارات الحالية:** التسجيل يتم مباشرة في `main.py`، ولا تظهر حزمة تجميع مركزية مثل `api/v1/router.py` في النسخة المفحوصة.
5. **لا ينبغي إنشاء Repository لكل نموذج تلقائياً:** نضيف طبقة وصول بيانات عندما تقلل التكرار أو تفصل استعلامات معقدة، لا لمجرد زيادة عدد الملفات.

### مبدأ التنظيم المقترح

ننتقل تدريجياً من الشكل العام الحالي إلى وحدات مجال مستقلة، مثلاً:
- `modules/learning/`: المناهج والمواضيع والدروس والتقدم.
- `modules/assessments/`: الاختبارات والأسئلة والنتائج والإتقان.
- `modules/classes/`: الفصول والتسجيل والواجبات حسب حدود المجال التي نعتمدها.
- `modules/files/`: بيانات الملفات والتخزين والتحقق.
- `modules/auth/` و`modules/users/`.
- `modules/billing/` و`modules/notifications/`.

يجب تحديد ملكية كل نموذج وخدمة قبل النقل؛ خصوصاً النماذج والخدمات المشتركة بين أكثر من مجال.

## 4. Frontend — الوضع الفعلي

### ما هو موجود

- React 19 وVite وTailwind CSS وi18next.
- `src/App.jsx` هو نقطة تجميع التطبيق الرئيسية.
- `src/components/` يحتوي مكونات كثيرة لميزات مثل التعلم والاختبارات والفصول والواجبات والفوترة والإدارة والملفات.
- `src/lib/` يحتوي عملاء API منفصلين للمصادقة والمناهج والاختبارات والواجبات والفصول والملفات والفوترة والإشعارات وغيرها.
- `src/hooks/` يحتوي حالياً hook لاتجاه RTL/LTR.
- `src/i18n.js` يهيّئ العربية والإنجليزية.
- توجد اختبارات مكونات بجانب بعض ملفات الواجهة.

### نقاط قوة موجودة

1. خدمات API مقسمة حسب المجال بدلاً من وضع جميع الطلبات في ملف واحد.
2. بعض الشاشات الكبيرة تُحمّل باستخدام React lazy loading.
3. إعدادات RTL/LTR وPWA موجودة.
4. توجد اختبارات للمكونات الأساسية مثل الاختبارات والموضوعات والواجبات والفصول.

### نقاط تحتاج إلى تنظيم

1. **مسؤوليات `App.jsx` كثيرة:** يتعامل مع المصادقة، بيانات المستخدم، الإشعارات وWebSocket، التنقل بين الشاشات، نوافذ الميزات، واللغة. كما يستخدم حالات متعددة من نوع `show...` للتحكم في عرض أجزاء مختلفة.
2. **التوجيه يدوي حالياً:** تُقرأ `window.location.pathname` وتُفحص مسارات محددة داخل `App.jsx` بدلاً من وجود طبقة Routes منظمة.
3. **المكونات مجمعة في مجلد واحد:** `components/` يحتوي على مكونات ميزات مختلفة مع المكونات العامة. الأفضل فصل مكونات الميزة عن العناصر المشتركة.
4. **خدمات API منفصلة، لكن حدود الميزات غير مكتملة:** ينبغي نقل كل API client مع المكونات والاختبارات ذات الصلة إلى مجلد الميزة المناسبة، مع ترك العميل العام والعناصر المشتركة في `shared/`.
5. **الترجمة تحتاج إلى تدقيق تغطية:** ملف `i18n.js` يحتوي مجموعة موارد صغيرة ظاهرة في الملف، لذا يجب حصر النصوص الثابتة في المكونات وتحديد فجوات الترجمة قبل توسيعها.
6. **التخزين الحالي للرموز:** `lib/api.js` يقرأ access token من `localStorage` ويرسله في Authorization header. هذا سلوك قائم يجب مراجعته ضمن تصميم المصادقة وحماية XSS/CSRF، وليس تغييره أثناء إعادة تنظيم المجلدات.

### مبدأ التنظيم المقترح

- `app/`: تهيئة التطبيق والتوجيه ومزودات السياق والتخطيطات.
- `features/<domain>/`: مكونات الميزة، hooks الخاصة بها، API الخاص بها، والاختبارات.
- `shared/`: المكونات العامة فعلاً، عميل HTTP المشترك، الأدوات العامة.
- `i18n/` و`styles/`: موارد الترجمة والأنماط العامة.

لا ننقل كل ما في `components/` إلى `shared/`; المكونات الخاصة بميزة تبقى داخل تلك الميزة.

## 5. الاختبارات وCI

حسب الملفات المفحوصة:
- Workflow الواجهة يشغّل تثبيت الحزم، اختبارات Vitest، بناء الإنتاج، وتدقيق الاعتماديات.
- Workflow الخلفية يشغّل تثبيت متطلبات الاختبار، ترحيلات Alembic، ثم pytest.
- ملف `frontend/package.json` يعرّف scripts للتطوير والبناء والمعاينة والاختبار، ولا يعرّف حالياً script مستقلاً لـ lint أو typecheck.
- اختبارات الواجهة موجودة بجانب مجموعة من المكونات، واختبارات الخلفية مجمعة تحت `backend/tests/`.
- إعدادات CI الحالية لا تمثل اختباراً شاملاً لمتصفح حقيقي متصل بنسخة منشورة من Backend وقاعدة البيانات.
- فحوصات CI على commit المفحوص `f3e7b899...` كانت ناجحة بحسب سجل التشغيل `41080298936`: 308 اختبار Backend و46 اختبار Frontend، مع نجاح الترحيلات وبناء الواجهة.
- سجل التشغيل أظهر أيضاً تحذيراً عن حجم حزمة الواجهة الرئيسية، إضافة إلى تنبيهات اعتماديات منخفضة الخطورة في التدقيق الكامل. اجتياز تدقيق الاعتماديات الإنتاجية لم يعنِ خلو جميع اعتماديات التطوير والاعتماديات العابرة من التنبيهات.

**تحسينات CI المقترحة:**
1. إضافة lint وفحص تنسيق/أنواع ملائمين للتقنيات المستخدمة بعد تحديد قواعد الفريق.
2. إضافة اختبارات تكامل للتدفقات الأساسية ذات المخاطر العالية.
3. إنشاء lockfile للواجهة واعتماد تثبيت حتمي بعد اختباره.
4. مراجعة نطاقات تشغيل workflow عند تغيّر بنية المشروع، بما فيها الوثائق والملفات المشتركة.
5. إضافة مسار اختبار متصفح فعلي قبل الإطلاق، منفصل عن اختبارات الوحدة الحالية.

## 7. المخاطر المعروفة التي تبقى خارج نطاق إعادة ترتيب الملفات

يجب ألا نخلط إعادة الهيكلة مع إصلاحات الأمن والتشغيل. تبقى هذه البنود أعمالاً مستقلة:
- حماية SSRF في LTI تحتاج إلى استكمال التحقق من أسماء DNS والعناوين التي تُحل إليها ومقاومة DNS rebinding وضوابط الخروج.
- لا يوجد حتى الآن فحص Malware مؤكد للملفات المرفوعة.
- يجب مراجعة Webhook idempotency لمنع معالجة الحدث المالي المكرر.
- تخزين رموز الدخول في `localStorage` يستلزم مراجعة أمنية وتصميماً انتقالياً متوافقاً مع حماية CSRF.
- تفعيل TLS/HTTPS يجب التحقق منه في بيئة النشر الفعلية.
- يجب إجراء اختبار تكامل حقيقي مع Moodle/Canvas قبل تفعيل LTI للإنتاج.
- يجب إجراء اختبار استعادة للنسخ الاحتياطية في بيئة غير إنتاجية.
- حجم الحزمة الرئيسية للواجهة يحتاج إلى تحليل وتقسيم إضافي.

## 8. قرارات فنية قبل أول نقل للملفات

قبل نقل أول وحدة إلى بنية `modules/` أو `features/`، نحتاج إلى:
1. اعتماد PR #4 وخط أساس موحد.
2. إعداد خريطة تبعيات للميزة المختارة: Routes → Services → Data access → Models، مع السماح بتجاوز طبقة فقط عندما تكون أبسط وأكثر وضوحاً.
3. تحديد مالك كل Model وSchema وService.
4. تحديد واجهات الاتصال بين المجالات ومنع استيراد Router من Router آخر.
5. تحديد طريقة الحفاظ على مسارات API الحالية حتى لا تتعطل الواجهة أو تكاملات العملاء.
6. تسجيل السلوك الحالي باختبارات قبل نقل الملفات.
7. تنفيذ النقل على دفعات صغيرة مع اختبارات بعد كل دفعة.

**القرار التنفيذي:** لا نبدأ بإعادة كتابة النظام ولا بنقل شامل للملفات. نعتمد خط الأساس بعد مراجعة PR #4، ثم نضع عقود الوحدات وننفذ مجالاً تجريبياً واحداً من البداية إلى الاختبار، وبعد نجاح النمط نعممه تدريجياً.
