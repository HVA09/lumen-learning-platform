## 1. القرار المعماري الرئيسي

اعتماد **Modular Monolith** في المرحلة الحالية:
- تطبيق Backend واحد وقاعدة بيانات PostgreSQL واحدة.
- وحدات داخلية واضحة حسب مجال العمل (Domain).
- عقود واضحة بين المجالات، مع منع الاستيراد المباشر من Router إلى Router.
- فصل منطق المجال عن FastAPI وSQLAlchemy بقدر عملي.
- لا نضيف Microservices أو قواعد بيانات منفصلة إلا عند وجود حاجة تشغيلية مثبتة.

الهدف هو وضوح المسؤوليات وسهولة الاختبار والصيانة، وليس زيادة عدد المجلدات أو الطبقات بلا فائدة.

## 2. الوضع الفعلي الذي تم فحصه

### Backend
- نقطة التشغيل **backend/app/main.py** تسجل المسارات باستيراد routers متعددة؛ الملف 121 سطرًا.
- البنية الحالية أفقية في معظمها: **auth/** و**routers/** و**models/** و**schemas/** و**services/**.
- **app/models/__init__.py** يستورد النماذج صراحةً لضمان تسجيلها في Base.metadata واكتشاف Alembic لها. يجب المحافظة على هذا التسجيل عند أي نقل مستقبلي.
- توجد خدمات منطقية خالصة قابلة للاختبار مستقلاً عن HTTP وقاعدة البيانات، منها **services/quiz_logic.py** و**services/question_analytics.py** و**services/spaced_repetition.py**.
- بعض routers ما زالت تجمع عمليات HTTP واستعلامات ORM وتنسيق خطوات أعمال متعددة. لا يعني ذلك وجوب إعادة كتابتها دفعة واحدة؛ نختار مجالاً محدوداً ونثبت طريقة فصل آمنة.

### Frontend
- الواجهة تستخدم React 19 وVite.
- **frontend/src/App.jsx** يبلغ 379 سطرًا في رأس الكود المفحوص، ويتولى حالة المصادقة واللغة وبعض النوافذ ومسارات العرض والتنبيهات، مع تحميل كسول لعدد من اللوحات.
- المكونات مجمعة غالبًا في **components/**، بينما عملاء API مقسمون إلى ملفات حسب المجال في **lib/**.
- يوجد عميل HTTP مركزي في **lib/api.js** يستخدم withCredentials وCSRF، وتعتمد جلسة المتصفح على Cookies من نوع HttpOnly. يجب الحفاظ على هذا التصميم خلال إعادة التنظيم.
- يجب حماية RTL/LTR واللغة العربية والإنجليزية وإمكانية الاستخدام عبر الهاتف في جميع خطوات النقل.

## 3. حدود المجالات المستهدفة

| المجال | الملكية المقترحة | المكونات الحالية التي ترتبط به |
|---|---|---|
| Identity & Access | الحسابات، الأدوار، المصادقة، الجلسات، 2FA | auth، User، AuthSession، مسارات المستخدم |
| Learning Catalog | المواد والمواضيع والدروس والمحتوى التعليمي | Subject، Topic، Lesson، TopicCard، curriculum/content |
| Assessments | بنك الأسئلة، الاختبارات، التصحيح ونتائج الأسئلة | Question، QuizAttempt، QuestionResult، quiz_logic.py، question_analytics.py |
| Learning Progress | الإتقان والنشاط والتقدم وتجميع نتائجه | TopicMastery، StudyDay، LessonProgress، reports |
| Review / Spaced Repetition | بطاقات المستخدم وخوارزمية SM-2+ | ReviewCard، spaced_repetition.py، SRS |
| Classes | الفصول والتسجيل ورموز الدعوة | ClassSection، ClassEnrollment، invite services |
| Assignments | الواجبات والتسليمات والتقييم | Assignment، AssignmentSubmission |
| Files | مرفقات المستخدم والتحقق والفحص والتخزين | FileAttachment، files router، malware scanner |
| Billing | الخطط والاشتراكات وأحداث الدفع | Plan، Subscription، ProcessedWebhookEvent، payment providers |
| Notifications | تخزين الإشعارات وقنوات التسليم | Notification، notifications router |
| LTI Integration | منصات LMS، OIDC، ربط الهوية وAGS | LTIPlatform، LTI routers/services |
| Gamification | الإنجازات والنقاط ولوحة المتصدرين | UserAchievement، achievements، streak logic |
| Administration & Audit | عمليات الإدارة والسجل التدقيقي | admin router، AuditLog |

### قواعد الملكية التي يجب حسمها
- User كيان هوية مركزي؛ لا ينبغي لكل مجال تعديل خصائص الحساب مباشرة. التغييرات الحساسة تمر عبر Identity.
- TopicMastery يقع بين Assessments وLearning Progress؛ التوصية أن تملك Progress سجل الإتقان، بينما يرسل Assessments نتيجة مصححة عبر عقد داخلي.
- Gamification يستهلك أحداثًا ونتائج من مجالات أخرى ولا يعيد تنفيذ التصحيح أو قواعد الإتقان.
- Reports قراءة وتجميع عابر للمجالات، ولا يصبح مالكًا لبياناتها الأصلية.
- Classes وAssignments منفصلان؛ لا يستورد أحدهما Router الآخر.
- app/models/__init__.py وAlembic يحتاجان خطة تسجيل للنماذج قبل أي نقل للملفات.

هذه الحدود نقطة بداية؛ لا تُحوّل إلى نقل ملفات نهائي قبل مراجعة استيرادات واستدعاءات كل مجال.

## 4. قواعد الاعتماديات المستهدفة

اتجاه Backend المقترح:

HTTP Router → Application Service / Use Case → Domain Rules → Ports / Data Access / External Adapters

- لا يستورد Router من Router آخر.
- لا يحتوي منطق المجال على كائنات Request أو Response أو تفاصيل FastAPI.
- يظل الوصول إلى ORM/قاعدة البيانات في طبقة التطبيق أو Data Access المناسبة.
- لا نفرض Repository لكل نموذج؛ نضيفه فقط عندما يقلل تعقيد الاستعلامات أو يوضح حدود البيانات.
- لا تعتمد وحدة على تفاصيل داخلية من وحدة أخرى؛ التواصل يكون عبر واجهة معلنة.
- تُحافظ مسارات API الحالية وعقود JSON أثناء إعادة الهيكلة ما لم يصدر قرار منفصل بتغييرها.

اتجاه Frontend المقترح:

app (routes, layouts, providers) → features/domain → shared

- كل Feature تملك مكوناتها وhooks وAPI helpers والاختبارات الخاصة بها.
- shared لا يستورد من features.
- عميل HTTP العام وتهيئة الجلسة تبقى مشتركة؛ API helpers الخاصة بمجال تنتقل معه.
- لا ننقل عنصرًا إلى Shared لمجرد أنه قابل للاستيراد؛ يجب أن يكون مشتركًا فعلًا.

### شروط قبول التجربة
- لا تغيير في API أو قاعدة البيانات أو Alembic migrations.
- جميع اختبارات منطق الاختبارات الحالية تنجح بلا تغيير متوقعاتها.
- جميع اختبارات Backend وFrontend وCI تنجح على أحدث commit.
- لا يوجد Router-to-Router import.
- يمكن التراجع عن التجربة بإعادة توجيه الاستيرادات إلى الواجهة القديمة دون استرجاع قاعدة البيانات.

لا نختار SRS أو Gamification كأول نقل كامل؛ فهما يعتمدان حاليًا على خدمات وموديلات من مجالات أخرى (activity/achievements/classes)، ويحتاجان خريطة تبعيات أدق.
