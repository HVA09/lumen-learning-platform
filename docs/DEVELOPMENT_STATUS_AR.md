> **الغرض:** هذا السجل هو نقطة المتابعة التشغيلية لخارطة الطريق المعمارية.  
> **آخر تحديث:** 2026-10-31  
> **المرجع الأساسي:** `docs/ARCHITECTURE_ROADMAP_AR.md`  
> **النطاق:** توثيق ومتابعة فقط؛ لا يغيّر سلوك التطبيق أو قاعدة البيانات.

## 1. القرار الهندسي المعتمد

تُعتمد `docs/ARCHITECTURE_ROADMAP_AR.md` باعتبارها المرجع الرئيسي لجميع أعمال تطوير Lumen. وترتبط بها كل مهمة جديدة من خلال تحديد المرحلة التي تخدمها، والملفات/المجالات المتأثرة، والاختبارات المطلوبة، ومخاطر التراجع.

المبادئ الملزمة:

1. اعتماد **Modular Monolith** حالياً، وعدم الانتقال إلى Microservices دون حاجة تشغيلية مثبتة.
2. تطوير تدريجي على فروع مستقلة؛ لا إعادة كتابة شاملة ولا تغييرات كبيرة مباشرة على `main`.
3. الحفاظ على الوظائف الحالية وعقود API وتوافق قاعدة البيانات أثناء إعادة الهيكلة.
4. كل تغيير برمجي يحتاج اختبارات مناسبة ومراجعة Diff وتوثيقاً مختصراً.
5. لا دمج قبل نجاح CI والمراجعة البشرية المطلوبة وموافقة مالك المشروع.
6. لا نشر إنتاجي قبل التحقق من الإعدادات والأمان والنسخ الاحتياطي والاستعادة والاختبارات الفعلية.
7. نجاح CI لا يُعد وحده دليلاً على الجاهزية للإنتاج.

## 4. ما نعرفه عن خط الأساس الحالي

بالنسبة إلى رأس طلب #4 المذكور أعلاه، تُظهر وثيقة الطلب وتشغيل CI:

- 308 اختبارات Backend ناجحة.
- 46 اختبار Frontend ناجحاً.
- نجاح تطبيق ترحيلات Alembic على PostgreSQL نظيف.
- نجاح بناء الواجهة.
- نجاح تدقيق الاعتماديات الإنتاجية.
- لا توجد مراجعة بشرية مسجلة في لقطة المراجعة التي فُحصت.
- لم يتم تنفيذ نشر إنتاجي.

أعمال لم تُغلق بعد، ولا يجوز اعتبارها منجزة لمجرد نجاح CI:

- منع SSRF عبر DNS والتحقق من العناوين التي تُحل إليها ومقاومة DNS rebinding في تكامل LTI.
- Idempotency موثوقة لأحداث الدفع Webhooks.
- مراجعة تخزين أسرار TOTP وتشفيرها.
- مراجعة تخزين الرموز في LocalStorage وتصميم Cookies آمنة وحماية CSRF.
- فحص Malware للملفات المرفوعة.
- إعداد HTTPS/TLS الفعلي في بيئة النشر.
- اختبار حقيقي لتدفق LTI مع Moodle أو Canvas.
- اختبار استعادة النسخ الاحتياطية.
- إضافة lockfile للواجهة، وتحسين تقسيم الحزم وأدوات جودة الكود.

## 5. قواعد اختيار أول وحدة لإعادة الهيكلة

لا نعتمد SRS أو أي مجال آخر كوحدة تجريبية نهائية اعتماداً على أسماء الملفات فقط. قبل الاختيار نُعدّ خريطة تتضمن:

1. ملفات Routes وSchemas وServices وModels وواجهات API ومكونات الواجهة ذات الصلة.
2. جميع الاستيرادات والاستدعاءات العابرة للمجالات.
3. عمليات قاعدة البيانات والترحيلات والقيود والفهارس ذات الصلة.
4. اختبارات الوحدة والتكامل والحالات السلبية المتاحة.
5. مخاطر تغيير السلوك وخطة التراجع.

بعد المقارنة نختار المجال الأقل مخاطرة والأوضح حدوداً والأفضل تغطية بالاختبارات. لا ننقل الملفات قبل تثبيت سلوكها الحالي باختبارات كافية.

## 6. قالب قبول أي مهمة تطوير جديدة

يجب أن تتضمن كل مهمة قبل تنفيذها:

- **المرحلة المرتبطة:** رقم المرحلة من خارطة الطريق.
- **الهدف والنطاق:** ما الذي سيتغير وما الذي لن يتغير.
- **الاعتماديات:** الملفات والمجالات والعقود المتأثرة.
- **المخاطر:** الأمان، البيانات، التوافق، الأداء وتجربة المستخدم.
- **الاختبارات:** اختبارات الوحدة والتكامل والبناء والفحوصات المناسبة.
- **خطة التراجع:** كيفية استعادة الحالة السابقة عند الفشل.
- **المراجعة:** رابط PR ونتائج CI وقرار المراجعة.

لا تُعد المهمة مكتملة حتى تُراجع النتائج ويُحدّث هذا السجل وخارطة الطريق عند الحاجة.
