# LUM-010 — تدقيق ملكية محتوى المنهج وصلاحيات المعلمين

**نوع العمل:** تدقيق قراءة فقط (Read-only security and authorization audit)  
**مرجع main المفحوص:** `5774c8575bf62a3894a0eb957b77745181ff71e1`  
**الفرع:** `audit/lum-010-content-ownership-20261118`  
**النطاق:** مسارات الأسئلة والدروس، نماذج Topic/Question/Lesson، اعتماديات RBAC، واختبارات المحتوى.  
**خارج النطاق:** تعديل سلوك الصلاحيات، migrations، تعديل بيانات، أو اختبار على إنتاج.

## 1. الخلاصة التنفيذية

- جميع مسارات `/content` المفحوصة تعتمد `require_teacher`، الذي يسمح بدورَي `teacher` و`admin` ويرفض الطالب.
- المسارات لا تطبق فحص ملكية لكل مورد عند القراءة أو الإنشاء أو التحديث أو الحذف أو التحليلات.
- `Question` يحتوي `created_by_user_id` ويُسجل منشئ السؤال عند الإنشاء، لكن هذا الحقل لا يُستخدم في تفويض التحديث/الحذف.
- `Lesson` لا يحتوي حقل منشئ أو مالك.
- `Topic` لا يحتوي حقل مالك أو منشئ؛ الدروس والأسئلة مرتبطة بالموضوع.
- الاختبارات الحالية تثبت منع الطالب ودورة CRUD للمعلم وإمكانية إدارة admin، لكنها لا تحتوي اختبارات صريحة لمعلم A مقابل محتوى أنشأه معلم B.
- لا يمكن تصنيف السماح الحالي كـIDOR مؤكد قبل حسم ما إذا كان محتوى المنهج مشتركاً بين المعلمين أم مملوكاً لمنشئه. الوثائق التشغيلية الحالية تصفه كإدارة لمحتوى منهج مشترك؛ لذلك هذا **قرار نموذج ملكية غير محسوم** مع فجوة اختبار، وليس ثغرة مثبتة بذاتها.

## 3. أدلة من الكود الحالي

### RBAC العام
- `backend/app/dependencies.py`: `require_teacher` يقبل `UserRole.teacher` و`UserRole.admin`، ويرفض غيرهما بـ403.
- `backend/app/routers/content.py`: جميع مسارات الإدارة أعلاه تعتمد هذه التبعية.

### السؤال
- `backend/app/models/question.py`: يحتوي `created_by_user_id` اختيارياً مع FK إلى users.
- `backend/app/routers/content.py`، `create_question`: يسجل `created_by_user_id=teacher.id`.
- `update_question` و`delete_question`: يجلبان السؤال بواسطة `db.get`/المعرّف ولا يقارنان `created_by_user_id` بالمستخدم الحالي.
- `list_questions` و`get_topic_question_analytics`: يعيدان محتوى/تحليلات الموضوع لكل مستخدم يملك دور teacher أو admin.

### الدرس والموضوع
- `backend/app/models/lesson.py`: لا يوجد `created_by_user_id` أو owner field في Lesson.
- `create_lesson` لا يسجل هوية المنشئ في سجل الدرس.
- `update_lesson` و`delete_lesson` لا يطبقان تحقق ملكية.
- `backend/app/models/topic.py`: لا يوجد owner field على Topic؛ النموذج مرتبط بـSubject.

## 4. تغطية الاختبارات الحالية والفجوة

الملف `backend/tests/test_content.py` يغطي:
- طلبات غير مصادق عليها: 401.
- الطالب لا يستطيع قراءة أو إدارة الأسئلة/الدروس: 403.
- المعلم يستطيع إنشاء/تحديث/حذف سؤال.
- المعلم يستطيع دورة حياة الدرس، مع إخفاء الدرس غير المنشور عن الطالب.
- admin يستطيع إدارة المحتوى.
- التحقق من صحة تعريف السؤال وتحليلاته.

**غير موجود في الاختبارات المفحوصة:**
- معلمان منفصلان A وB، حيث ينشئ A سؤالاً/درساً ثم يحاول B قراءته أو تعديله أو حذفه.
- اختبارات cross-teacher على analytics أو قوائم موضوعات/دروس.
- اختبار صريح يثبت أن المحتوى المزروع (seeded) مشترك ولا يملك منشئاً فردياً، أو يحدد قواعد تحريره.

## 5. التقييم الأمني

| المسألة | التقييم |
|---|---|
| منع الطالب من مسارات الإدارة | مغطى باختبارات حالية |
| وصول admin | مقصود بحسب التبعية الحالية |
| وصول معلم إلى محتوى معلم آخر | مسموح حالياً ضمنياً؛ يتوقف تصنيفه على سياسة الملكية |
| غياب فحص owner على Question CRUD | فجوة تفويض إذا كان المحتوى خاصاً؛ ليس خللاً مؤكداً إذا كان المحتوى مشتركاً |
| عدم وجود owner في Lesson | يتطلب قرار نموذج بيانات إذا اختيرت الملكية الفردية |
| اختبار cross-teacher | فجوة اختبار مؤكدة |

## 6. خيارات سياسة الملكية

**A — محتوى خاص بالمنشئ:** القراءة والكتابة للمنشئ وadmin فقط. يتطلب ملكية للدروس، قواعد واضحة للمحتوى المزروع، وفحص صلاحية على كل مسار؛ وقد يغير تجربة المعلمين الحالية.

**B — منهج مشترك مع كتابة مقيدة (التوصية):** القراءة متاحة للمعلمين ضمن المنهج المشترك؛ التعديل والحذف للمنشئ وadmin؛ المحتوى المزروع/المشترك يديره admin أو دور تحريري معتمد. يتطلب تحديد كيفية التعامل مع الأسئلة القديمة التي يكون منشئها NULL، وإضافة owner للدروس إذا كانت الدروس التي ينشئها المعلم خاصة به.

**C — منهج مشترك بالكامل:** جميع المعلمين يستطيعون القراءة والإنشاء والتعديل والحذف ضمن المنهج المشترك، مع توثيق هذا القرار وإضافة اختبارات cross-teacher تثبت السلوك المقصود. هذا هو الأقرب إلى السلوك الحالي، لكنه يوسع أثر أي خطأ أو حذف غير مقصود.

## 7. التوصية والبوابة المطلوبة

التوصية الهندسية المبدئية هي **B** لأنها تفصل القراءة التعليمية المشتركة عن صلاحية تغيير المحتوى، وتحد من أثر الحذف/التعديل العرضي. لكنها ليست قراراً معتمداً من مالك المنتج.

**لا تنفذ أي تغيير في الصلاحيات أو schema أو migrations قبل اعتماد A أو B أو C.** بعد الاعتماد:
1. أضف اختبارات cross-teacher إيجابية وسلبية لكل endpoint متأثر.
2. عرّف سياسة الأسئلة المزروعة والأسئلة القديمة ذات `created_by_user_id=NULL`.
3. إذا لزم owner للدروس، أعد خطة migration قابلة للرجوع مع backfill موثق؛ لا تخمّن مالكاً للسجلات القديمة.
4. اختبر المعلم وadmin والطالب، و404/403 لمنع كشف وجود الموارد عند الحاجة.
5. أعد فحوص Backend/Frontend/E2E وراجع أثر API/UI قبل الدمج.

## 8. فحص مقارن لمسارات أخرى ذات ملكية موارد

أُجري مسح ساكن أولي لبقية ملفات `backend/app/routers` لتحديد نمط التفويض المستخدم في موارد أخرى. النتائج التالية مؤشرات من الكود وليست إغلاقاً لتدقيق RBAC/IDOR الكامل:

| المجال | نمط الحماية الملحوظ | دلالة المقارنة |
|---|---|---|
| الفصول `classes.py` | `_get_owned_class_or_404` يربط الفصل بالمعلم الحالي؛ عمليات التعديل/الحذف/إدارة الطلاب تستدعيه | يوجد نمط ملكية مورد صريح في المنتج نفسه |
| الواجبات `assignments.py` | `_can_manage` يسمح للمنشئ أو admin؛ إدارة التسليمات والتقييم تمر عبر `_get_manageable_assignment` | نموذج ملكية واضح للموارد المنشأة |
| الملفات `files.py` | الاستعلامات تقيد `FileAttachment.user_id` بالمستخدم الحالي في العرض والتنزيل والحذف | عزل مباشر لملفات المستخدم |
| الإشعارات `notifications.py` | القراءة والتأشير كمقروء تقيدان `Notification.user_id` بالمستخدم الحالي | عزل على مستوى السجل |
| الاختبارات `quiz.py` | جلب المحاولة والتاريخ مقيدان بـ`QuizAttempt.user_id` | منع الوصول لمحاولات مستخدم آخر |
| بطاقات المراجعة `srs.py` | CRUD والمراجعة والتصدير تقيد `ReviewCard.user_id` بالمستخدم الحالي | عزل بيانات الطالب الشخصية |
| الفوترة `billing.py` | الاشتراك والإلغاء مقيدان بـ`Subscription.user_id` الحالي؛ الخطط عامة | عزل بيانات الاشتراك |
| الإدارة `admin.py` وتهيئة LTI `lti.py` | المسارات الإدارية المقروءة محمية بـ`require_admin` | فصل صلاحية الإدارة عن صلاحية المعلم |

هذا يوضح أن غياب فحص الملكية في `content.py` ليس النمط الوحيد المتاح؛ توجد أمثلة فعلية داخل Lumen لفحص ملكية المورد. لكنه لا يحسم هل المحتوى التعليمي نفسه مشترك أم خاص. لا يجوز نسخ قاعدة الواجبات أو الفصول إلى الدروس والأسئلة آلياً قبل قرار المنتج.

**نطاق المسح المقارن:** جرى استخراج مسارات HTTP واعتمادياتها وفحص مؤشرات الملكية في الملفات المذكورة. لم تُراجع جميع فروع كل handler أو جميع اختبارات كل مجال، ولم يُنفذ اختبار هجومي ديناميكي.

## 9. حدود هذا التدقيق

هذا تدقيق ساكن على ملفات main عند SHA المذكور. لم نشغّل التطبيق أو الاختبارات محلياً، ولم نختبر إنتاجاً، ولم نعدّل كوداً أو قاعدة بيانات. لا يغلق LUM-010 بالكامل؛ يغلق فقط خطوة جرد مسارات المحتوى والأدلة الأولية، ويبقى قرار الملكية واختبارات cross-teacher والتدقيق الأوسع لبقية RBAC/IDOR مفتوحاً.

## 10. توسيع المراجعة إلى مسارات RBAC/IDOR الأخرى

أُجريت مراجعة ساكنة إضافية على ملفات المسارات والاختبارات المشار إليها أدناه في فرع `main` وقت هذه الجولة. الغرض مقارنة ضوابط الوصول واكتشاف المسارات التي تستحق اختبارات إضافية؛ لا تمثل هذه المراجعة اختباراً ديناميكياً شاملاً.

| المجال | الضابط الذي ظهر في التنفيذ | دليل الاختبار/المراجعة | النتيجة الأولية |

### مسارات عامة مقصودة

- `GET /curriculum/subjects` و`GET /curriculum/topics/{topic_id}` متاحان دون تسجيل دخول في التنفيذ الحالي.
- `backend/tests/test_curriculum.py` يثبت أن قائمة المواد عامة (`test_list_subjects_is_public_and_seeded`) ويختبر تفاصيل الموضوع دون مصادقة (`test_get_topic_detail`).
- لا أصنف هذه المسارات كـIDOR لمجرد غياب المصادقة؛ يجب أن تبقى عامة فقط إذا كان نشر بيانات الموضوع ومخرجات التعلم مقصوداً. يجب ألا تتضمن الاستجابة بيانات خاصة أو أسئلة بإجاباتها أو سجلات طلاب.

### نقاط تحتاج استكمالاً قبل إغلاق LUM-010

1. **المحتوى المشترك:** حسم سياسة A/B/C في القسم 6، ثم إضافة اختبارات cross-teacher لكل مسار content المتأثر، بما فيها التحليلات وقوائم المحتوى.
2. **لوحة المتصدرين العامة:** مراجعة DTO والحقول المعروضة وسياسة الموافقة/الظهور، وتحديد هل أسماء الطلاب والنقاط عامة لجميع المستخدمين المسجلين أم يجب حصرها.
3. **SRS:** إضافة اختبار cross-user صريح لمحاولة قراءة/تعديل/حذف بطاقة مستخدم آخر، حتى مع وجود قيد `user_id` في الاستعلام.
4. **تغطية الاختبارات:** فحص بقية فروع handlers والـWebSocket وعمليات التصدير/الاستيراد ومسارات التكامل، وربط كل endpoint باختبار مصادقة ودور وملكية/عضوية مناسب.
