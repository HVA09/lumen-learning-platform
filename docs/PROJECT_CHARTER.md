# ميثاق مشروع Lumen Learning Platform

آخر تحديث: 2026-11-02

هذا الملف هو المرجع الدائم لأهداف المشروع والقيود والقرارات العامة. عند اختلاف محادثة قديمة مع هذا الملف أو مع ملفات الحالة الأحدث، يجب التحقق من سجل القرارات وملف الحالة وGit قبل اتخاذ أي إجراء.

## 1. الهدف

إنشاء منصة تعليمية عربية/إنجليزية ذات بنية هندسية منظمة وآمنة وقابلة للقراءة والصيانة والتطوير والتوسع. يجب أن تكون عملية الاستخدام واضحة على الهاتف والحاسوب، وألا تُضاف ميزات شكلية على حساب الاستقرار أو حماية البيانات.

## 2. قيود المستخدم الثابتة

- الميزانية الحالية: صفر.
- لا توجد بطاقة إلكترونية أو وسيلة دفع متاحة للمستخدم.
- لا تعتمد الخطة الأساسية على خدمة مدفوعة أو تجربة مجانية تتطلب بطاقة.
- لا تُفعّل بوابة دفع أو اشتراكات مدفوعة في النسخة المجانية. إعداد الدفع الافتراضي المعتمد هو التعطيل.
- المستودع عام لتجنب تكاليف الخصوصية/الاستضافة المدفوعة؛ لذلك يُمنع وضع مفاتيح أو كلمات مرور أو بيانات شخصية أو أسرار تشغيلية فيه.
- يحتاج المستخدم إلى متابعة العمل من أكثر من جهاز، غالبًا عبر الهاتف؛ لذلك يجب أن تكون خطواته قليلة وواضحة، وأن لا يعتمد استمرار المشروع على جهاز واحد أو جلسة Codespaces.
- يفضّل المستخدم تجاوز المراجعة البشرية اليدوية الاختيارية. لا يجوز مع ذلك تخطي اختبارات CI أو فحوصات الأمن أو متطلبات حماية الفرع المفروضة من GitHub، ولا يجوز الادعاء بوجود مراجعة بشرية لم تحدث.

## 3. المبادئ الهندسية

1. **التصميم قبل التوسع:** حافظ على حدود واضحة بين الواجهة والخلفية وقاعدة البيانات والخدمات والتشغيل.
2. **تغييرات صغيرة قابلة للتراجع:** لا تنفذ إعادة كتابة واسعة لمجرد تحسين شكلي.
3. **الأمان افتراضيًا:** أقل صلاحية ممكنة، تحقق من المدخلات، إدارة أسرار خارج Git، فشل مغلق في ضوابط الأمان الحساسة.
4. **الاختبار قبل الدمج:** اختبارات backend وfrontend والبناء وفحوصات الاعتماديات والأسرار مطلوبة لكل تغيير مؤثر.
5. **عدم إخفاء الفشل:** لا تجعل الواجهة تتقدم وكأن الحفظ نجح عندما تفشل الشبكة أو API.
6. **قابلية التشغيل:** وثّق إعداد البيئة والنسخ الاحتياطي والاستعادة والترحيل والتراجع.
7. **التوافق مع الموارد المجانية:** لا تفترض توفر ذاكرة كبيرة أو تخزين دائم أو SMTP أو نطاق أو بطاقة دفع قبل التحقق من مزود الاستضافة.
8. **حماية البيانات:** لا تستخدم بيانات إنتاج حقيقية في الاختبارات أو المستودع العام.

## 4. التقنية الحالية

- الواجهة: React + Vite.
- الخلفية: FastAPI / Python.
- قاعدة البيانات: PostgreSQL.
- توجد مكونات تشغيل مساندة مثل Redis وCelery وClamAV وNginx وعمليات النسخ الاحتياطي.
- راجع ملفات README الخاصة بكل جزء وملفات Compose وملفات البيئة النموذجية قبل أي تعديل تشغيلي. لا تستنتج وجود جاهزية إنتاجية لمجرد وجود إعدادات في المستودع.

## 5. سياسة الدفع والاستضافة

- يجب أن تعمل الوظائف الأساسية المجانية دون تفعيل الدفع.
- يبقى مزود الدفع معطّلًا إلى أن يطلب المستخدم خلاف ذلك صراحةً وتتوفر لديه وسيلة قانونية وآمنة للإعداد.
- لا تسجل المستخدم في خدمة مدفوعة ولا تنشئ موارد قد تتحول إلى فاتورة.
- قبل اختيار استضافة، تحقق من حدود الخطة الحالية، وطلب البطاقة، ومدة الاحتفاظ بالتخزين، وحدود النوم/التوقف، وحدود قاعدة البيانات.
- لا تصف خطة بأنها مجانية أو بلا بطاقة دون تحقق حديث من شروطها.

## 6. سياسة المراجعة والدمج

- المستخدم يفضل عدم جعل المراجعة البشرية الاختيارية عائقًا دائمًا.
- لا تختلق موافقة أو مراجعة. دوّن بوضوح ما إذا كانت المراجعة البشرية لم تحدث.
- لا تتجاوز فحوصات CI المطلوبة أو حماية الفرع. إذا منع GitHub الدمج بسبب قاعدة حماية أو موافقة مطلوبة، اشرح المانع ولا تتحايل عليه.
- لا تدمج PR ولا تنشر إنتاجًا قبل نجاح الفحوصات على أحدث commit بالضبط، والتحقق من حالة الدمج، ومعرفة مخاطر الترحيل والنسخ الاحتياطي.
- افصل بين: اجتياز الاختبارات، مراجعة الكود، جاهزية التشغيل، والنشر الفعلي. هذه حالات مختلفة.

## 7. مصادر الحقيقة وترتيبها

1. Git commit الحالي والملفات الفعلية في الفرع المستهدف.
2. `docs/PROJECT_STATUS.md` للحالة الراهنة والبوابات المتبقية.
3. `docs/DECISIONS.md` للقرارات وسجل أسبابها.
4. `docs/CONTINUITY.md` لاستعادة السياق عبر الأجهزة والمحادثات.
5. نتائج GitHub Actions وPull Requests وروابط commits.
6. المحادثات القديمة: مصدر سياقي مساعد فقط، وليست بديلًا عن التحقق من المستودع.

عند وجود تعارض، تحقّق من أحدث commit ونتائج CI وحدّث الوثائق بدل تكرار معلومات قديمة.

## 8. معيار قبول أي ميزة

لا تعتبر الميزة مكتملة إلا إذا:
- اتضح سلوكها وحالات الخطأ والصلاحيات.
- أضيفت/حُدّثت الاختبارات المناسبة.
- نجح CI على commit المقصود.
- وُثّقت الإعدادات والأثر التشغيلي عند الحاجة.
- لم تُسجل أسرار أو بيانات حساسة.
- حُدّث ملف الحالة وسجل القرار إذا تغيرت بنية المشروع أو سياسته.
