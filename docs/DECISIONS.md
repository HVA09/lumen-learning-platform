# سجل قرارات مشروع Lumen

آخر تحديث: 2026-11-04

يسجل هذا الملف القرارات التي اتُّخذت، والتوصيات الهندسية التي اعتُمدت في مسار العمل، وأسبابها وآثارها. لا يعني إدراج توصية أن المستخدم وافق عليها؛ تُذكر جهة القرار وحالته صراحةً.

## طريقة قراءة السجل

- **معتمد — تفضيل المستخدم:** طلب المستخدم القرار بوضوح.
- **معتمد تشغيليًا — توصية هندسية:** اختيار هندسي اتُّبع لتنظيم العمل أو تقليل المخاطر، ويمكن مراجعته إذا ظهرت أدلة أفضل.
- **معلّق:** لا يجوز تنفيذه قبل استكمال المعلومات أو الاختبار.
- **مرفوض/ملغى:** لا يُعاد العمل به دون قرار جديد موثق.

كل قرار جديد يضيف: التاريخ، الحالة، القرار، الجهة، السبب، الأثر، وطريقة التراجع عند الحاجة. لا تحذف القرارات القديمة؛ أضف قرارًا لاحقًا يوضح أنها استُبدلت.

## ADR-001 — GitHub هو سجل المشروع الدائم

- التاريخ: 2026-11-02
- الحالة: **معتمد تشغيليًا — توصية هندسية**
- القرار: حفظ ميثاق المشروع والقرارات والحالة وخطوات استعادة السياق داخل `docs/` في المستودع.
- السبب: محادثات ChatGPT قد لا تظهر على جهاز آخر بسبب حساب مختلف أو إعدادات/مشكلة مزامنة أو استخدام محادثة مؤقتة؛ كما أن سياق المحادثة لا ينبغي أن يكون المصدر الوحيد للقرارات.
- الأثر: يمكن فتح الملفات نفسها من GitHub على أي جهاز، ويمكن بدء محادثة جديدة مع رابط المستودع وملف الحالة.
- القيد: يجب ألا يحتوي المستودع العام على أسرار أو بيانات شخصية.

## ADR-002 — إبقاء المشروع مجانيًا وعدم اشتراط الدفع

- التاريخ: 2026-11-02 (تفضيل مستمر سبق أن ذكره المستخدم)
- الحالة: **معتمد — تفضيل المستخدم**
- القرار: الأولوية لاستضافة وأدوات مجانية لا تطلب بطاقة، وعدم إنشاء موارد مدفوعة أو تفعيل الدفع الإلكتروني.
- السبب: الميزانية صفر ولا توجد بطاقة أو وسيلة دفع متاحة.
- الأثر: نختار الخدمات بعد التحقق من شروطها الحالية، وقد نحتاج إلى تقليل مكونات التشغيل أو استخدام بديل أبسط إذا كانت الخطة المجانية لا توفر موارد كافية.
- حد القرار: لا نقدم وعودًا بأن منصة كاملة عالية الموارد ستعمل مجانًا إلى الأبد.

## ADR-003 — إبقاء مستودع GitHub عامًا مع حماية الأسرار

- التاريخ: 2026-11-02 (بناءً على طلب المستخدم السابق)
- الحالة: **معتمد — تفضيل المستخدم**
- القرار: الإبقاء على `HVA09/lumen-learning-platform` عامًا.
- السبب: تجنب التكاليف والحفاظ على وصول سهل من عدة أجهزة.
- ضوابط إلزامية: عدم رفع ملفات البيئة الحقيقية أو الرموز أو مفاتيح التشفير أو كلمات المرور أو بيانات المستخدمين. فحص الأسرار لا يعوض عن تدوير أي سر حقيقي سبق كشفه.

## ADR-004 — الدفع معطل في النسخة المجانية

- التاريخ: 2026-11-02
- الحالة: **معتمد تشغيليًا — توصية هندسية متوافقة مع تفضيل المستخدم**
- القرار: `PAYMENT_PROVIDER=disabled` افتراضيًا، ولا يتم استدعاء checkout/cancellation كمسار دفع فعّال عند التعطيل.
- السبب: عدم وجود وسيلة دفع لدى المستخدم، وتجنب ربط إطلاق المنصة ببوابات مالية.
- الأثر: لا تفعّل Stripe أو PayPal ولا تضف أسرارها حتى يصدر طلب صريح وتتوفر المتطلبات.

## ADR-005 — العمل عبر فرع تطوير وPull Request بدل الكتابة المباشرة إلى main

- التاريخ: 2026-11-02
- الحالة: **معتمد تشغيليًا — توصية هندسية**
- القرار: تجميع العمل الحالي في PR #4 على فرع `fix/security-production-hardening`، وترك `main` محميًا.
- السبب: تقليل احتمال إفساد الفرع الافتراضي وإتاحة فحص التغييرات قبل اعتمادها.
- الأثر الحالي: PR #4 مفتوح وغير مدمج. آخر main المعروف هو `da33265617b61baaccdea05de5015f73bd1b5d56`. آخر head موثق عند إنشاء هذا السجل هو `89891d1d520555beed5a3e6013c05d6ae14ae7a9`.
- ملاحظة: لا يُفترض أن كل ما على فرع PR أصبح موجودًا في main.

## ADR-006 — الاختبارات وفحوصات الأمن لا تُتجاوز

- التاريخ: 2026-11-02
- الحالة: **معتمد تشغيليًا — توصية هندسية**
- القرار: لا دمج ولا نشر قبل نجاح الفحوصات على أحدث commit بالضبط، بما فيها backend وfrontend/build وفحص الأسرار.
- السبب: كثرة الإضافات دون اختبارات موثوقة ترفع احتمال إدخال أعطال أو تسريب بيانات.
- الأثر: طلب المستخدم تجاوز المراجعة البشرية الاختيارية لا يساوي السماح بتعطيل CI أو تجاوز حماية GitHub.

## ADR-007 — فحص الأسرار التاريخية مع استثناءات ضيقة فقط

- التاريخ: 2026-11-02
- الحالة: **معتمد تشغيليًا — توصية هندسية**
- القرار: تنفيذ فحص Gitleaks لنطاق التغييرات والتاريخ الكامل، وعدم استثناء مجلد الاختبارات أو قاعدة الكشف كاملة. تُستثنى بصمات محددة بعد مراجعة أنها قيم اختبار وهمية.
- السبب: المستودع عام، وقد تظهر أسرار قديمة في تاريخ Git أو أرشيفات مضمنة.
- الأثر: استثناء fingerprint لا يثبت وحده أن القيمة آمنة؛ يجب إعادة فحص أي نتيجة جديدة. إذا ظهر سر حقيقي، يوقف النشر ويُلغى/يُدوّر السر لدى مزوده.

## ADR-008 — عدم ادعاء جاهزية الإنتاج قبل اختبار البيئة الحقيقية

- التاريخ: 2026-11-02
- الحالة: **معتمد تشغيليًا — توصية هندسية**
- القرار: فصل نجاح الاختبارات الآلية عن جاهزية الاستضافة والنشر.
- السبب: SMTP وHTTPS وClamAV وLTI والنسخ الاحتياطي الخارجي ومفاتيح الإنتاج تحتاج إعدادًا واختبارات على البيئة المستهدفة.
- الأثر: لا نقول "تم النشر" أو "جاهز للإنتاج" قبل وجود دليل تشغيل فعلي.

## ADR-009 — لا تعتمد استعادة المشروع على ذاكرة المحادثة

- التاريخ: 2026-11-02
- الحالة: **معتمد — طلب المستخدم وتوصية هندسية**
- القرار: في نهاية كل مرحلة تطوير، حدّث `PROJECT_STATUS.md` و`DECISIONS.md` عند تغير القرارات، وسجّل commit وPR ونتائج CI والمهام القادمة.
- السبب: المستخدم يتنقل بين جهازين وقد يبدأ محادثة جديدة.
- الأثر: يمكن متابعة العمل من ملف الحالة حتى عند فقدان المحادثة؛ لا يمكن لهذا الإجراء وحده إصلاح مزامنة سجل ChatGPT، لكنه يمنع فقدان سجل المشروع.

## ADR-010 — عدم تجاوز شرط الموافقة الإلزامي في حماية main

- التاريخ: 2026-11-02
- الحالة: **معتمد تشغيليًا — قيد GitHub مفروض**
- الجهة: قيد من إعدادات المستودع؛ مع توصية هندسية بالالتزام به.
- القرار: لا نزوّر مراجعة بشرية ولا نحاول التحايل على شرط الموافقة. نواصل التطوير على فرع العمل حتى تُستوفى قاعدة GitHub أو يغيّر مالك المستودع إعدادها صراحةً.
- السبب: محاولة دمج PR #4 بعد نجاح CI #509 رُفضت من GitHub برسالة HTTP 405 التي تشترط موافقة واحدة من مراجع لديه صلاحية كتابة. قائمة المراجعات الحالية فارغة. أدوات الاتصال المتاحة لا تملك صلاحية إدارة إعدادات الحماية.
- الأثر: PR #4 ما زال مفتوحًا، و`main` لم يتغير. نجاح CI لا يعادل موافقة المراجع المطلوبة.
- الخيارات النظامية: موافقة مراجع موثوق بصلاحية كتابة، أو تعديل مالك المستودع إعداد عدد الموافقات المطلوبة إلى صفر عبر واجهة GitHub بعد فهم أثر تقليل الحماية.
- التراجع أو الاستبدال: يمكن للمالك إعادة عدد الموافقات المطلوب إلى قيمته السابقة. لا ينشأ أي تغيير في الحماية تلقائيًا من هذا القرار.


## ADR-011 — عدم نشر المكدس الكامل على خطة مجانية غير كافية

- التاريخ: 2026-11-02
- الحالة: **معتمد تشغيليًا — توصية هندسية**
- الجهة: توصية هندسية مبنية على وثائق مقدمي الخدمات، ومتوافقة مع شرط المستخدم (صفر ميزانية وعدم توفر بطاقة).
- القرار: لا ننشر كامل الحزمة الحالية على مضيف مجاني بذاكرة 512 MB، ولا نعطّل ClamAV أو النسخ الاحتياطي لجعلها تعمل على خطة أصغر. يمكن استخدام الاستضافة المجانية لمعاينة الواجهة الثابتة أو تجربة مكونات منفصلة ببيانات اصطناعية فقط.
- السبب: Render وKoyeb Free يقدمان 512 MB تقريبًا؛ Render Free يوقف الخدمات الخاملة ويفقد الملفات المحلية وينهي PostgreSQL المجاني بعد 30 يومًا. Supabase Free قاعدة محدودة تتوقف عند قلة النشاط. Cloudflare Pages مناسب للملفات الثابتة وليس حاوية FastAPI مجانية. ClamAV يوصي بما لا يقل عن 3 GiB RAM تقريبًا و3–4 GiB للخوادم والحاويات.
- الأثر: يبقى النشر الإنتاجي معلقًا حتى تتوفر بيئة ملائمة بلا تكاليف ولا بطاقة، أو تتم إعادة تصميم ميزات محددة بطريقة آمنة ومختبرة. لا نستخدم Oracle Free لأن التسجيل يتطلب بطاقة.
- التراجع أو الاستبدال: إذا تغيرت موارد الخطة أو سياسة البطاقة، نعيد التقييم استنادًا إلى وثائق المزود الحالية واختبار نشر تجريبي؛ لا نفعّل رفع الملفات من دون فحص برمجيات خبيثة يعمل فعليًا.


## ADR-012 — إعادة تأسيس سلسلة LTI المتباعدة قبل إدخالها

- التاريخ: 2026-11-02
- الحالة: **معتمد تشغيليًا — توصية هندسية**
- الجهة: توصية هندسية مستندة إلى مقارنة commit graphs وملفات التغيير، وليست طلبًا لتفعيل LTI فورًا.
- القرار: إبقاء PRs #16–#23 كمسودات منفصلة الآن. بعد حسم PR #4، تُعاد تهيئة السلسلة على `main` الحالي بالترتيب، ثم تُحل تعارضات ملفات LTI المشتركة وتُختبر من جديد. لا ندمج الفروع القديمة مباشرة إلى PR #4 أو `main`.
- السبب: السلسلة متباعدة عن فرع PR #4، وتعدّل ملفات LTI أساسية مشتركة وتضيف migrations `0023` و`0024` وواجهة إدارة AGS. الاختبارات التاريخية الناجحة لا تثبت التوافق مع خط الأساس الحالي.
- الأثر: نحافظ على ميزات AGS وواجهة الإدارة والاختبارات دون فقدها أو تكرارها، ونمنع استبدال كود أحدث بطريق الخطأ.
- التراجع أو الاستبدال: يمكن إدخال كل PR مستقلًا بعد إعادة تأسيسه واختباراته؛ إذا ظهرت تعارضات غير آمنة، نحتفظ به معلقًا حتى مراجعة مخصصة. لا تُغلق أي مسودة قبل حفظ تغييراتها الفريدة.


ملاحظة تحديث ADR-011 بتاريخ 2026-11-02: تمت مراجعة حدود الخدمات من الوثائق الرسمية مجددًا. تم تثبيت موارد Pages/Workers وContainers، Render Free، Supabase، Neon، Upstash، Koyeb وClamAV في `HOSTING_FEASIBILITY.md`. لا تزال النتيجة كما هي: استضافة الواجهة الثابتة ممكنة تجريبيًا، أما المكدس الكامل فيحتاج موارد أكبر من الخطط المجانية التي راجعناها. عدم توافر البطاقة لم يتم إثباته بالنسبة إلى Supabase وNeon وKoyeb، لذلك لا تُدرج هذه الخدمات ضمن توصية بلا بطاقة قبل تجربة التسجيل.


## ADR-013 — اعتماد Modular Monolith واختيار تجربة Assessments الخالصة

- التاريخ: 2026-11-02
- الحالة: **معتمد تشغيليًا — توصية هندسية متوافقة مع هدف المستخدم**
- الجهة: توصية هندسية مبنية على فحص الكود الحالي؛ هدف التنظيم والصيانة والأمان هو تفضيل مستمر لدى المستخدم.
- القرار: المحافظة على Modular Monolith، وعدم الانتقال إلى Microservices. تبدأ إعادة التنظيم البرمجية بعد حسم PR #4، بتجربة صغيرة هي استخراج quiz_logic.py إلى modules/assessments/domain مع طبقة توافق مؤقتة.
- السبب: منطق الاختبارات الحالي مستقل عن FastAPI وSQLAlchemy ويملك اختبارات وحدات واضحة. نقل هذا المنطق وحده يثبت نمط التنظيم دون إعادة كتابة النظام أو تغيير واجهات API.
- الأثر: أول خطوة معمارية قابلة للقياس والتراجع. لا تغييرات DB أو migrations أو behavior ضمن التجربة.
- التراجع أو الاستبدال: الإبقاء على services/quiz_logic.py كواجهة توافق يسمح بإعادة الاستيرادات للمسار السابق. لا تبدأ التجربة قبل اعتماد خط الأساس في main.


## ADR-014 — تطبيق قفل محاولات TOTP الفاشلة على تسجيل الدخول

- التاريخ: 2026-11-02
- الحالة: **مطبق على فرع PR #4، CI #521 ناجح**
- الجهة: توصية أمنية هندسية أُدخلت كإصلاح دفاعي.
- القرار: تُحتسب رموز TOTP الخاطئة بعد كلمة المرور الصحيحة ضمن عدّاد محاولات الحساب نفسه `failed_login_attempts`. عند بلوغ `MAX_FAILED_LOGIN_ATTEMPTS` يُضبط `locked_until` وفق `ACCOUNT_LOCKOUT_MINUTES` ويُسجّل حدث تدقيق ويُرسل إشعار أمني. لا يُحتسب غياب الرمز (استجابة 428) محاولة خاطئة؛ لأنه طلب لمتابعة تحدي العامل الثاني وليس تخمينًا.
- السبب: الاقتصار على عدّاد كلمة المرور يترك تخمين العامل الثاني بلا قفل حسابي.
- التحقق: أُضيف اختبار يفعّل TOTP، ويتأكد أن غياب الرمز لا يرفع العداد، ثم يرسل رموزًا خاطئة حتى حد القفل، ويتأكد أن الرمز الصحيح لا يتجاوز القفل. CI #521: 402 اختبار خلفية و51 اختبار واجهة؛ بناء الإنتاج وفحص التاريخ الكامل ناجحة.
- الأثر: لا تغيير في API أو قاعدة البيانات أو migrations. إعادة استخدام سياسة القفل الحالية يقلل اختلاف السلوك بين عاملي المصادقة.
- التراجع: إزالة فرع العدّاد الجديد والاختبار المرتبط به فقط إذا أثبتت القياسات أو مراجعة أمنية أن سياسة القفل المشتركة تسبب أثرًا جانبيًا؛ لا يُلغى حد محاولات العامل الثاني دون بديل موثق.


## ADR-015 — معالجة بصمات بيانات الاختبار بعد squash merge

- التاريخ: 2026-11-02
- الحالة: **معتمد تشغيليًا — معالجة محدودة بانتظار تحقق CI**
- القرار: عند squash merge لـ PR #4، أعاد Gitleaks اكتشاف 52 قيمة `generic-api-key` في commit الدمج الجديد. تمت معاينة كل موضع في 13 ملفًا تحت `backend/tests/`; القيم كلها كلمة المرور الاصطناعية المشتركة `StrongPass123` المستخدمة لاختبارات التكامل، وليست بيانات اعتماد تشغيل.
- المعالجة: إضافة fingerprints الـ52 الدقيقة (commit + file + rule + line) إلى `.gitleaksignore`. لا يُستثنى أي مسار كامل، ولا تُعطّل قاعدة Gitleaks أو وظيفة الفحص. يجب أن ينجح CI على PR الإصلاح، بما في ذلك فحص `--all --full-history`, قبل إغلاق هذه المعالجة.
- السبب: استثناءات البصمات الأصلية كانت مرتبطة بـ SHA commits ما قبل الدمج؛ squash merge أعاد إسناد محتوى الاختبارات إلى SHA جديد.
- الأثر: يبقى فحص الأسرار شاملاً، مع توثيق نتائج الاختبارات الوهمية المعروفة على نحو قابل للتدقيق.
- التراجع: يمكن حذف هذه الـ fingerprints الدقيقة إذا أزيلت القيم من التاريخ أو تغيّرت طريقة الفحص؛ لا يُستخدم استثناء واسع لمجلد الاختبارات.

- تنبيه minimatch: [GHSA-g3hv-75wg-m249](https://github.com/advisories/GHSA-g3hv-75wg-m249) يصيب ما قبل 11.0.1؛ الإصلاح 11.0.1. الإصدارات الموجودة 10.2.6 و5.1.9 ضمن النطاق المتأثر، ويتعلق الأمر بتضخم globParts وإمكانية استهلاك CPU/ذاكرة عند معالجة أنماط يتحكم بها المهاجم.
- تتبع `ejs` و`jake` و`filelist` في npm audit يعود إلى اعتماد filelist على minimatch، وليس دليلاً بحد ذاته على أن EJS 3.1.10 مصاب بالثغرة القديمة التي أُصلحت في 3.1.10؛ انظر [ejs issue #797](https://github.com/mde/ejs/issues/797). كما أبلغ npm audit عن `@trickfilm400/rollup-plugin-off-main-thread` ضمن السلسلة القديمة؛ يجب اختبار تحديثه إلى إصدار متوافق بدلاً من افتراض توافقه.
- القرار: لا تُطبّق `npm audit fix --force` ولا تخفّض `vite-plugin-pwa` من 2.0.0 إلى 1.1.0 لمجرد اقتراح الإصلاح الآلي. هذا تغيير major عكسي محتمل، ولا يوجد دليل بعد على أنه يحافظ على سلوك PWA الحالي. صفحة الحزمة تعرض 2.0.0 كالإصدار الأحدث وقت هذا التدقيق: [npm vite-plugin-pwa](https://www.npmjs.com/package/vite-plugin-pwa).
- خطة المعالجة: افحص أولاً إصداراً لاحقاً من Workbox يوسّع حدود glob/minimatch ويحدّث OMT؛ وإن لم يتوفر، اختبر overrides محددة على فرع مستقل، مع توليد lockfile بواسطة npm نفسه. شروط القبول: `npm ci` ناجح، جميع اختبارات Frontend ناجحة، `vite build` يولّد Service Worker بنجاح، فحص PWA/precache/runtime cache لا يتغير سلوكه، وتقرير `npm audit` يثبت اختفاء التنبيهات المستهدفة دون إدخال تنبيهات جديدة.
- أحدث قائمة خرجت من CI #419047: تنبيهان Low (`@rollup/plugin-node-resolve`, `deepmerge`) وأربعة Moderate (`glob`, `minimatch`, `vite-plugin-pwa`, `workbox-build`). أظهر تشغيل #418769 السابق أيضاً تنبيهات `@trickfilm400/rollup-plugin-off-main-thread` و`ejs` و`filelist` و`jake` ضمن عدده الأعلى؛ لا نمحو الدليل السابق ولا نفترض أن كل تنبيه سابق ما زال يظهر في أحدث لقطة.
- النطاق الحالي: **لا تغييرات على package.json أو package-lock أو كود التطبيق في PR #69**. لا تُعدّ التنبيهات الحالية عالية أو حرجة؛ لكنها لا تُغلق حتى تُعالج أو يوثّق سبب عدم قابلية التحديث مع مراجعة دورية.
- التراجع عن تجربة مستقبلية: إزالة override والعودة إلى lockfile السابق المعروف، ثم `npm ci` والاختبارات والبناء. لا تغيّر API أو DB أو migrations أو إعدادات الاستضافة.


## ADR-034 — إدخال Browser E2E حقيقي تدريجيًا باستخدام Playwright

- التاريخ: 2026-11-04
- الحالة: **منفذ ومُدمج — PR #70 وPR #73 (Squash Merge)**

- القرار: إضافة وظيفة CI مستقلة باسم `Browser E2E (registration and browser session)` تستخدم Playwright for Python **1.64.1** مع Chromium، وتشغّل نسخة Vite production preview متصلة بخادم FastAPI حقيقي وقاعدة PostgreSQL وRedis مؤقتتين في GitHub Actions.
- النطاق: `frontend/e2e/smoke_test.py` و`frontend/e2e/requirements.txt` وملف `.github/workflows/ci.yml`. تثبيت Playwright منفصل عن npm manifest و`package-lock.json` حتى لا يغيّر اعتماديات الواجهة أو lockfile.
